## 1. Предназначение

ЕО-42 е минимална система за връзка между софтуерен агент и отдалечена Unix машина.

Моделът е умишлено ограничен:

```text
        агент
          │
          │ TCP
          │ ChaCha20
          ▼
     ┌────────────┐
     │ agentshell │
     └─────┬──────┘
          │
          ├── команда
          ├── stdout/stderr
          └── exit status
```

Системата не реализира терминал, shell протокол, multiplexing или универсален RPC механизъм.

Основната операция е:

```text
COMMAND → STREAM → EXIT
```

Допълнително е реализиран транспорт на файлове.

## 2. Конструкция

ЕО-42 използва предварително споделен 256-bit ключ.

При установяване на TCP връзката не се извършва преговор на протокол, алгоритми или идентичност.

```text
TCP connection
      │
      ▼
   salt block
      │
      ▼
encrypted frames
      │
      ▼
command / data / end
```

Ключът се подава от оператора. Способността да се дешифрира трафикът е необходимото удостоверяване за тази експериментална система.

Няма:

- сертификати
- host keys
- CA
- алгоритъмно договаряне
- интерактивен handshake
- session negotiation

## 3. Криптографски транспорт

### 3.1 Шифър

| Параметър | Стойност |
|---|---|
| cipher | `ChaCha20` |
| variant | `djb` |
| key | `256 bit` |
| nonce | `64 bit` |
| MAC | няма |

ChaCha20 се използва като потоков шифър.

ЕО-42 не предоставя криптографска автентикация на пакетите. Това е съзнателно ограничение на образеца.

## 4. Начален salt

Всяка посока започва с 64 байта, получени чрез:

```text
ct = ChaCha20(key, BASE) XOR random64
```

Получателят не дешифрира блока. Използва:

```text
seed = ct[56:64]
```

за последващото генериране на nonce.

Посоките използват различни базови стойности:

| Посока | Базова стойност |
|---|---|
| CLIENT → SERVER | `BASE_C = FF81FFFF3E420818` |
| SERVER → CLIENT | `BASE_S = 007E0000C1BDF7E7` |

`BASE_S` е битово допълнение на `BASE_C`.

## 5. Кадриране

Всяко съобщение започва с `[len: u32 BE][data]`.

След това се добавя нулево запълване до размер, кратен на 64 байта.

```text
┌──────────────┬──────────────────────┐
│ length 4 B   │ payload              │
└──────────────┴──────────────────────┘
                         │
                         ▼
                    zero padding
                         │
                         ▼
                    64 B blocks
```

Максималният размер на един транспортен пакет е:

```text
16 blocks × 64 B = 1024 B
```

По-големите съобщения се предават като последователност от такива пакети.

## 6. Nonce последователност

Всеки пакет има номер `p`. `p` се увеличава в рамките на TCP връзката и никога не се нулира между отделни команди.

За блок `j`:

```text
j % 16 == 0   →  nonce = seed + p

иначе         →  nonce = последните 8 байта
                 на предходния ciphertext block
```

При препълване на uint64 се извършва wraparound.

Тази схема осигурява непрекъсната nonce верига в рамките на връзката.

## 7. Протокол

### 7.1 Client → Server

| Съобщение | Условие | Значение |
|---|---|---|
| Команда | `len > 0`, `payload[0] != 00` | payload-ът представлява команден ред |
| Качване | `len > 0`, `payload[0] == 00` | резервираният magic за file upload |
| Drop | `len == 0` | клиентът прекратява връзката |

### 7.2 Server → Client

| Съобщение | Условие | Значение |
|---|---|---|
| DATA | `len > 0` | payload-ът съдържа част от обединения `stdout + stderr` |
| END | `len == 0` | следва `[status: u32 BE]` |

Статусът е:

| Стойност | Значение |
|---|---|
| `0..255` | exit status |
| `1000 + N` | процесът е прекратен от сигнал N |
| `126` | операторът е отказал изпълнението |

## 8. Изпълнение на команди

ЕО-42 не използва shell.

Командният ред има форма:

```text
ENV1=value ENV2=value CWD=/path /bin/program arg1 arg2
```

Токенизацията е whitespace-based. Не съществуват:

- quotes
- escaping
- pipes
- redirection
- `$(...)`
- globbing
- shell expansion

**Правила**

- Токените преди binary-то, съдържащи `=`, стават environment variables: `FOO=bar` се превръща в env променлива `FOO=bar`.
- `CWD=` има специално значение и не се предава като environment variable.
- Първият токен без `=` е executable path. Следващите токени стават `argv[]`.

## 9. File upload

Ревизия 2 добавя директен транспорт на файлове.

Формат:

```text
00
path_len   u16 BE
path       path_len bytes
size       u64 BE
data       size bytes
```

Ограничения:

- `path_len > 0`
- `path_len <= 4096`
- `size <= 1 GiB`
- `path` не съдържа `00`

Размерът трябва да удовлетворява:

```text
size = msg_len - 11 - path_len
```

Несъответствие води до прекратяване на връзката.

- Директорията трябва да съществува.
- Съществуващ файл се отваря с `O_TRUNC`.
- Данните се записват потоково с 4 KiB буфер. Целият файл не се зарежда в паметта.

При успех:

```text
upload: OK <size> B -> <path>
END 0
```

При грешка:

```text
upload: FAIL ...
END 1
```

При операторски отказ: `END 126`.

Остатъкът от съобщението се прочита и изхвърля при отказ или грешка, така че nonce последователността остава синхронизирана.

## 11. Изпълнителна среда

Основният образец е реализиран като статичен ELF без libc. Целевата реализация използва директни Linux system calls.

Процесът за изпълнение на binary се създава чрез:

```text
clone(CLONE_VM | CLONE_VFORK)
```

Binary-то може да бъде заредено в memfd. След това се изпълнява чрез:

```text
execveat()
```

Така изпълнимият файл не е необходимо да остава на диска.

Изходът на child процеса се пренасочва към pipe. `stdout` и `stderr` се обединяват.

## 13. Операторска защита

Сървърът може да бъде стартиран с `--yn`. При този режим всяка команда изисква локално потвърждение.

```text
[agentshell] команда от агента:

  CWD=/ /bin/uname -a

изпълнение? y/n:
```

При `y`, `Y`, `д`, `Д` командата се изпълнява.

При `n`, `N`, `н`, `Н` се връща:

```text
[agentshell] отказано от оператора (y/n)
```

и `END 126`. Връзката остава активна.

EOF на stdin се третира като отказ. Невалиден отговор води до повторно запитване.

## 14. Сигнали

Сървърът обработва: `SIGINT`, `SIGTERM`, `SIGHUP`, `SIGQUIT`.

При получаване:

- текущото изпълнение се прекратява;
- child процесът получава `SIGKILL`;
- логът се затваря;
- процесът излиза нормално.

Например при `SIGINT`:

```text
Ctrl+C
   │
   ▼
SIGINT
   │
   ▼
terminate child
   │
   ▼
flush log
   │
   ▼
exit 0
```

Linux x86-64 изисква валиден `SA_RESTORER` при съответната употреба на `rt_sigaction`. Липсващ restorer адрес води до дефектно връщане от signal handler.

## 15. Одитен журнал

При стартиране сървърът създава `DD-MM-YYYY_HH-MM-SS.txt` в текущата работна директория. При повторно стартиране в същата секунда файлът се отваря с `O_APPEND`.

Журналът съдържа:

- startup
- connections
- client addresses
- handshake
- commands
- operator decisions
- command output
- exit status
- disconnects
- shutdown

Контролни байтове в output-а се записват като `\xHH`. UTF-8/кирилица се записва без преобразуване.

Всеки лог ред има формат:

```text
[DD-MM-YYYY HH:MM:SS] event
```

Записът на един лог ред се извършва с един `write(2)`.

Ако журналът не може да бъде създаден, сървърът извежда предупреждение и продължава без него.

Часовата зона се задава чрез константата `TZ_OFFSET` в `agentshell.asm`.

## 17. Клиент

Еталонният клиент е написан на Python 3 и не използва външни библиотеки.

Пример:

```python
from agentshell import AgentShell

c = AgentShell("host", 1124, hex_key)

for chunk in c.run("CWD=/ /bin/ls"):
    print(chunk, end="")

print(f"[exit {c.last_exit}]")
```

Интерактивен режим:

```bash
python3 agentshell.py host 1124 <key>
python3 agentshell.py host 1124 <key> --yn   # клиентска операторска защита
```

Качване:

```python
c.upload("/local/file", data)
```

или в интерактивен режим:

```text
@put /local/file /remote/file
```

## 18. Компилация

Необходим е NASM и GNU linker.

```bash
nasm -f elf64 agentshell.asm -o agentshell.o
ld -o agentshell agentshell.o
```

Банерът `ISOM.ANSI` се вгражда в binary-то по време на компилация. След компилация изпълнимият файл не зависи от наличието на `ISOM.ANSI` в работната директория.

**Бърз старт (Debian/Ubuntu):**

```bash
apt-get install screen nasm openssl
```

Сесия screen:

```bash
screen -d -m -S agentshell   # създава отделена сесия още преди стартирането на сървъра
screen -r agentshell         # прихваща сесията обратно
```

Генериране на ключ, компилация и стартиране:

```bash
KK=$(openssl rand -hex 32)
echo $KK
nasm -f elf64 agentshell.asm -o agentshell.o
ld -o agentshell agentshell.o
./agentshell --selftest
./agentshell 1124 $KK
```

Отделяне на сесията: `Ctrl+A`, след това `D` — отделя сесията, без да спира сървъра.

`KK` е 256-битов ключ, генериран локално от `openssl`. Той се съобщава на клиента.

## 20. Известни ограничения

ЕО-42 е тестов образец. Следните ограничения са част от конструкцията:

| Ограничение | Последствие |
|---|---|
| Няма MAC | ciphertext manipulation не се открива криптографски |
| PSK | ключът трябва да бъде разпределен извън протокола |
| Няма replay защита | записан трафик може да бъде преизпълнен при подходящи условия |
| Един worker | една активна команда |
| Няма timeout | блокираща команда блокира worker-а |
| Няма shell | липсват shell конструкции |
| Няма quoting | аргументите са whitespace-separated |
| Грешен ключ | резултатът е garbage и връзката се прекратява |
| Няма multiplexing | една логическа операция наведнъж |

> Тези свойства не са дефекти, прикрити от интерфейса. Те са границите на експеримента.

## 21. Обхват

ЕО-42 не е предназначен да замести SSH. Не е:

- production remote administration system
- general-purpose RPC framework
- terminal protocol
- authentication infrastructure
- secure file transfer standard

Предназначението му е по-тясно:

> Да се провери колко малък може да бъде practically usable криптиран транспорт за command-oriented software agent.

## 22. Номер 42
